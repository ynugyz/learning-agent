## Verdict summary

The four contracts are readable, honestly labelled drafts, and their
counterexample tables are better than most. The problem is that the three
guarantees they lead with are not in the machine contract. "Every assertion is
traceable" (SC-2), "the card is an index and no field accepts note prose"
(SC-1/F1), and "absence is never silently equivalent to a default" (RM-4/RM-11)
are all falsifiable by documents that validate against the shipped schemas —
and in two places the specs explicitly claim a rejection (`evidenceRef` that
"identifies nothing", `{kind: opaque, value: ""}`) that the schema cannot
perform. Second, the SourceMap quietly crosses the layer boundary it was built
to defend: `disposition.knowledgeRefs` stores `knowledgeId`s in a Layer B
artifact, in direct contradiction of SM-3 as written in §6, and two
`processingHints` values (`may-duplicate-existing-knowledge`,
`likely-correction-to-existing`) can only be produced by doing Layer D work.
Third, `RunManifest.runtime.resolution` is unfillable — no contract anywhere
records a *requested* runtime — so RM-2's requested-versus-actual invariant is
false for exactly the artifact whose purpose is comparison validity. A large
set of smaller divergences (schema vs TypeScript vs spec vs ARCHITECTURE) is
listed below; the TypeScript drafts in particular have never been compiled, so
nothing has yet checked that they even agree with each other.

## Findings

### CH-01 — The traceability guards are presence checks, not content checks, and the specs claim otherwise
- Severity: blocker
- Confidence: CONFIRMED
- Location: `schemas/semantic-card.v0.1.schema.json` `$defs.evidenceRef` (L14–30, `anyOf` L28; `locator` L22 has no `minLength`); `schemas/source-map.v0.1.schema.json` `$defs.locator` (L29–44, `anyOf` L42; `start`/`end`/`value` have no `minLength`); claims of enforcement at `specs/semantic-card-v0.1.md` L169–170 and `specs/source-map-v0.1.md` L188–191 + F9 (L353)
- Problem: The only mechanism that makes a claim traceable is "the reference must identify something", and it is implemented as `required`-on-a-key, never as non-emptiness. `{"sourceUnitId": ""}`, `{"locator": ""}`, `{"kind": "opaque", "value": ""}` and `{"kind": "span", "start": ""}` all validate. The SemanticCard spec states "an evidence reference that identifies nothing is rejected"; the SourceMap spec states `kind: opaque` is permitted "**only** with a non-empty `value`" and counterexample F9 states `{kind: opaque, value: ""}` is "Untraceable; rejected". Neither rejection exists. JSON Schema *can* express both (the file already uses `minLength` elsewhere and `if/then` in `agent-runtime.v0.1.schema.json` L222–225), so this is not a tooling limitation.
- Why it matters: An implementation can satisfy the schema completely while every provenance reference points at the empty string. The failure this produces is precisely `EVID-PROVENANCE-LOST` / `SEM-LINK-BROKEN`, which these contracts cite as their motivation (`source-map-v0.1.md` L41, `ERROR_TAXONOMY.md` L41, L64). Any downstream audit that trusts "the schema validated" would be reading a guarantee that does not exist.
- Evidence: `"anyOf": [{ "required": ["sourceUnitId"] }, { "required": ["locator"] }]` (card schema L28) with `"locator": { "type": "string" }` (L22) — no `minLength`, no `pattern`.
- Suggested direction (not a mandate): either add `minLength: 1` to the identifying members and an `if/then` for `kind: opaque`, or delete the enforcement claims from the specs and state plainly that identifying-ness is a validator rule.

### CH-02 — "The card is an index, no free-floating prose" is false in the machine contract
- Severity: blocker
- Confidence: CONFIRMED
- Location: `schemas/semantic-card.v0.1.schema.json` `claims` (L108–124, `anyOf` L122, `note` L112), `semanticCore.summary` (L59–63), `sectionIndex[].gist` (L95–98); `specs/semantic-card-v0.1.md` SC-1 (L19–34), SC-2 invariant table (L233), F1 (L319); `schemas/source-map.v0.1.schema.json` `notes` (L202–205) with `specs/source-map-v0.1.md` F1 (L345); `schemas/run-manifest.v0.1.schema.json` `notes` (L162–165) with RM-6 (L182)
- Problem: SC-2's executable statement is "Every machine assertion is traceable to a note anchor or an evidence reference. No free-floating prose field exists." Three counterexamples are in the same contract. (1) `claims[]` requires only `epistemicState` plus **at least one of** `anchor` / `note`, so `{"note": "<arbitrary prose>", "epistemicState": "verified"}` — no anchor, no evidence, no `basis` — is valid. (2) `semanticCore.summary` is required, unbounded, has no anchor and no evidence field, yet is unambiguously an assertion about the concept. (3) `SourceMap.notes` and `RunManifest.notes` are unbounded free strings defended only by "Not a place for lesson content" / "Must not contain conclusions", which no validator can read. SC F1's claim that "No field accepts note prose" and "An implementer doing this has to add a field, which is a visible contract change" is therefore wrong: `claims[].note`, `semanticCore.summary` and both `notes` fields accept it today, with no contract change.
- Why it matters: This is the contract's headline defence against the semantic layer becoming a second, worse human note (`AGENTS.md` §7, SC-1). As written, the defence depends entirely on implementer virtue, and the cheap path for a lazy implementation is to dump prose into `claims[].note` and skip anchor resolution entirely (which is also the harder engineering problem, per SC-A5).
- Evidence: `"required": ["epistemicState"], "anyOf": [{ "required": ["anchor"] }, { "required": ["note"] }]` (card schema L121–122); spec E1 wording at L233 vs `note` L112 described only as "Short label only. Not authoritative prose."
- Suggested direction (not a mandate): make `claims[].anchor` required (or add a `claimId`), and decide explicitly whether a `notes` string belongs in either artifact at all.

### CH-03 — "Absence must be visible" enums, and `integrity.state`, can assert everything and contain nothing
- Severity: blocker
- Confidence: CONFIRMED
- Location: `schemas/run-manifest.v0.1.schema.json` `model.resolved` (L82–90, `value` L85, `required: ["availability"]` L88), `caseId` (L31–40, `value` L35, `required: ["availability"]` L38), `model` (L78–94: root requires `model` at L169 but the object has no required members); `schemas/semantic-card.v0.1.schema.json` `integrity` (L210–227, `required: ["state"]` L225, `checkedAt` L215, `checkedAgainst` L216–223) with `cardFingerprint` (L54) and `humanNoteFingerprint` (L86) both optional; claims at `specs/semantic-card-v0.1.md` SC-6/F6 (L77–83, L324) and `specs/run-manifest-v0.1.md` RM-4/RM-11 (L38–43, L183)
- Problem: The "explicit unknown" mechanism is defeated wherever the enum can assert presence without the value being required. `{"model": {"resolved": {"availability": "reported"}}}` validates while reporting nothing; `{"caseId": {"availability": "present"}}` validates with no case; `"model": {}` validates even though RM-2's whole point is recording which model ran. Most seriously, `integrity.state: "ok"` validates on a card that carries **no fingerprint at all** (`cardFingerprint` and `humanNoteFingerprint` are both optional, `checkedAt` is optional), which is exactly the F6 scenario SC-6 claims to prevent ("Requires a fingerprint on both sides; with only a note-side hash, 'card edited' is undetectable"). SC §6 does say these invariants are "the invariants a future validator should enforce", but SC-6/F6 and RM-4/RM-11 are stated as contract behaviour, not as aspirations, and the corresponding constraints are expressible in the schema.
- Why it matters: `RunManifest` exists to answer "is comparing this run with another valid?" (RM-1). A manifest that asserts `reported`/`present`/`matched` without values is indistinguishable from a truthful one at validation time, so an automated comparison gate cannot be built on it. `integrity.state: ok` is the field a future writer would gate on before touching knowledge; an unfalsifiable `ok` makes the gate decorative.
- Evidence: card schema `"required": ["state"]` (L225) with no dependency on either fingerprint; manifest schema `"required": ["availability"]` (L88) with no dependency on `value`.
- Suggested direction (not a mandate): use `if/then` (`availability: reported` ⇒ `required: ["value"]`; `state: ok` ⇒ both fingerprints required) or state in the specs that these three guards are advisory.

### CH-04 — `RunManifest.runtime.resolution` cannot be computed: no requested runtime is recorded anywhere
- Severity: major
- Confidence: CONFIRMED
- Location: `specs/run-manifest-v0.1.md` §1 RM-2 (L25–30), §3 `runtime` (L91–94), §6 RM-2 (L180), example L205; `schemas/run-manifest.v0.1.schema.json` `runtime` (L63–77, `required: ["kind","version","resolution"]` L75); `schemas/agent-runtime.v0.1.schema.json` `runtimeMetadata` (L9–27) and `taskRequest` (L42–118)
- Problem: RM-2 states "Every 'what we asked for' field is therefore paired with a 'what actually happened' field (`RM-8`, `RM-9`, `RM-10`)" and RM-2 in §6 states requested and actual are "separately representable for model, runtime and reasoning". There is no requested runtime field in any of the four contracts: `RunManifest.runtime` has `kind`, `version`, `resolution` and no `requested`; `RuntimeMetadata` declares only what *is* installed; `TaskRequest` has no runtime field (correctly, since it is the runtime-neutral port). `resolution: "matched"` in the manifest example (L205) therefore asserts something no producer can establish.
- Why it matters: The manifest is the artifact that decides whether two runs are comparable. If `runtime.resolution` can only honestly be `unknown`, the field adds no protection against the substitution RM-2 calls "the most common invisible cause of an invalid comparison" — for the runtime, that is. Meanwhile the field's presence implies the check happened.
- Evidence: run-manifest schema `"required": ["kind", "version", "resolution"]` (L75) with properties `kind`, `version`, `resolution` only (L67–73).
- Suggested direction (not a mandate): either record the expected runtime (e.g. from run configuration) so the comparison is real, or drop `resolution` here and let the manifest state the version only.

### CH-05 — `disposition.knowledgeRefs` puts `knowledgeId`s in a Layer B artifact, contradicting SM-3 and SM-22 as written
- Severity: major
- Confidence: CONFIRMED
- Location: `schemas/source-map.v0.1.schema.json` `disposition.knowledgeRefs` (L166), `disposition` required per unit (L173); `specs/source-map-v0.1.md` §3.2 (L165), §6 SM-3 (L233), SM-22 (L237), `specs/source-map-v0.1.md` F2 (L346) and F12 (L356); mitigation claim at A7 (L380–382)
- Problem: SM-3's executable statement is "**No field value may be derived from a LessonModel id, a `knowledgeId`, or an alignment decision.**" `disposition.knowledgeRefs` is an array of `knowledgeId`s, present on every unit, and its documented purpose (SM-6) is to be filled in by Layers C/D/E after the map is "complete". The spec's reconciliation ("the slot is the seam", L80) works for `disposition.state`, which is a controlled vocabulary of the map's own making, but not for a field whose values are foreign keys minted downstream. Likewise SM-22's "it references none of them except through `disposition`" is an exception clause that swallows the rule once the exception is a required per-unit object. The consequence A7 acknowledges is only the write-later/immutability cost; the SM-3 contradiction is not acknowledged anywhere.
- Why it matters: This is the concrete instance of the dependency the SourceMap contract declares it will never have. It gives Layer C a mutation obligation on Layer B, and it means a unit's recorded content changes when unrelated knowledge is created — which is the process SM-3 says would force the map to be rewritten whenever understanding improves (L46–49).
- Evidence: spec field table L165 — "`disposition.knowledgeRefs` … `knowledgeId`s it contributed to" — versus the SM-3 invariant at L233: "No field value may be derived from a LessonModel id, a `knowledgeId`, or an alignment decision."
- Suggested direction (not a mandate): either narrow SM-3 to unit identity (which is what its rationale argues) or move the knowledge-facing half of disposition out of the map.

### CH-06 — Two `processingHints` values require the existing knowledge network, which Layer B is defined not to consult
- Severity: major
- Confidence: CONFIRMED
- Location: `schemas/source-map.v0.1.schema.json` `processingHints[].hint` enum (L141–148: `may-duplicate-existing-knowledge`, `likely-correction-to-existing`); `specs/source-map-v0.1.md` §5 (L220), SM-3 (L233), SM-1 (L19–32); `docs/ARCHITECTURE.md` Layer B (L45–50)
- Problem: `may-duplicate-existing-knowledge` and `likely-correction-to-existing` are alignment judgements (Layer D's `NO_CHANGE`/`CORRECT` territory, `ARCHITECTURE.md` L74–78) embedded as hints in the map. ARCHITECTURE §2 defines Layer B as modelling what the lesson contains "**before** consulting the existing knowledge network too heavily, so that incoming material is not distorted by prior beliefs", and SM-3 forbids values derived from an alignment decision. A correct value for these two hints cannot be obtained at the stage that owns the field — so either the field is filled from knowledge-network access that Layer B is supposed to avoid, or it is guesswork recorded with the same schema shape as an observation.
- Why it matters: The map's whole framing (SM-1, SM-5) is that it describes the package and holds cheap, overturnable guesses. These two hints import the most drift-prone judgement in the system into the artifact that is supposed to be stable across reprocessing, and their `advisory: true` marker does not make them *producible*.
- Evidence: hint enum L145–146; ARCHITECTURE L45–50; SM-3 L233.
- Suggested direction (not a mandate): move knowledge-relative hints out of the map (they belong to Layer D), or record that the map may read the knowledge index and drop the "before consulting" claim.

### CH-07 — Required `retentionClass` is a significance judgement, contradicting SM-1's "described, not interpreted"
- Severity: major
- Confidence: CONFIRMED
- Location: `schemas/source-map.v0.1.schema.json` `$defs.retentionClass` (L19–23: `core`, `pedagogical-aid`, `assessment-relevant`, …), required per unit (L173); `specs/source-map-v0.1.md` SM-1 (L19–32), field table (L151), SM-4 (L54–62), SM-5 (L64–70), A4 (L370–372)
- Problem: SM-1 says units "are described, not interpreted" and "nothing in the map asserts what a unit *means* for the knowledge base", and SM-5 says early judgements were made "not … with full lesson understanding" — which is why hints are optional and pinned advisory. Yet `retentionClass` is **required** on every unit and its values (`core`, `pedagogical-aid`, `assessment-relevant`) are exactly claims about knowledge significance. The contract therefore mandates the strong judgement at the cheap stage and merely permits the weak one. A4 discusses whether `retentionClass` is derivable from `contentType`, but not the SM-1 contradiction.
- Why it matters: A judgement that is required cannot be deferred, so the map acquires a pedagogical verdict before the lesson is understood — and per A3 (contentType `unknown`) that verdict is the only thing standing between the ledger and a uniformly `droppable` list. Contrast with the intended shape (SM-1: a paper about presence and coverage).
- Evidence: `retentionClass` M in the field table (L151) with the enum's own description "Why a unit matters for later processing" (schema L21) vs SM-1 L29–30.
- Suggested direction (not a mandate): allow `unclassified`/defer retention, or split "what is here" (required) from "how much it matters" (advisory, like hints).

### CH-08 — `Usage` diverges between the TypeScript mirror and the RunManifest schema, and the divergence rejects a valid runtime result
- Severity: major
- Confidence: CONFIRMED
- Location: `src/contracts/run-manifest.ts` L16 (`import type { Usage } from './agent-runtime'`) and L154 (`readonly usage?: Usage`); `src/contracts/agent-runtime.ts` L150–156 (`cost` L155); `schemas/run-manifest.v0.1.schema.json` `usage` (L137–147, no `cost`, `additionalProperties: false` L146); `schemas/agent-runtime.v0.1.schema.json` `usage.cost` (L128–136); `specs/run-manifest-v0.1.md` RM-17 (L118)
- Problem: In TypeScript the manifest reuses the runtime contract's `Usage`, which includes `cost`. In JSON Schema the manifest declares its own inline `usage` object with the same four members minus `cost` and `additionalProperties: false`. So a manifest that aggregates a runtime `Usage` object — the obvious implementation of "Aggregate usage, mirroring the runtime boundary" (RM-17) — typechecks and then fails schema validation. Two spellings of one shape, in the same contract set, is a drift generator, and the failure only appears at validation time in a real run.
- Why it matters: RM-17's stated intent is achieved in one mirror and violated in the other. Whichever mirror an implementer reads first determines whether `cost` is passed through, and the manifest is the artifact least tolerant of "this run failed validation for a reason you did not expect".
- Evidence: TS `readonly usage?: Usage` (run-manifest.ts L154) where `Usage` has `readonly cost?: { amount: number; currency: string }` (agent-runtime.ts L155) vs schema `usage.properties` = `inputTokens`, `outputTokens`, `totalTokens`, `availability` (L140–143) with `additionalProperties: false` (L146).
- Suggested direction (not a mandate): pick one definition and `$ref` / re-export it, or record in the manifest schema whether `cost` is deliberately excluded (RM-Q5 asks the same question).

### CH-09 — Three incompatible "where did this come from" shapes; a `TaskRequest` cannot express a SourceMap locator
- Severity: major
- Confidence: CONFIRMED
- Location: `schemas/semantic-card.v0.1.schema.json` `$defs.evidenceRef` (L14–30); `schemas/source-map.v0.1.schema.json` `$defs.locator` (L29–44) + `sources[].sourceId` (L55); `schemas/agent-runtime.v0.1.schema.json` `input[].ref` (L70–78); acknowledged weakly at `specs/agent-runtime-v0.1.md` RT-A5 (L402–403)
- Problem: Provenance is modelled three times with three shapes. The card's `EvidenceRef` is `{sourceUnitId?, locator?: string, note?}`. The map's locator is a structured `{kind, start, end, value}` plus a separate `sourceId` on the unit. The runtime request's `input[].ref` is `{sourceId?, sourceUnitId?, locator?: string}` — no `note`, and `locator` is a free string. Consequently a caller building a `TaskRequest` from a SourceMap unit cannot carry that unit's locator (`kind`/`start`/`end`) at all: it must flatten to an uninterpretable string or drop it. RT-A5 says these "may duplicate `EvidenceRef`" and that sharing is "possibly" desirable; the understatement is that they are not interchangeable. In practice the richest locator in the system cannot be attached to the context item that consumes the evidence.
- Why it matters: `EVID-PROVENANCE-LOST` is defined as "A claim cannot be traced back to its source location" (`ERROR_TAXONOMY.md` L41). The contracts lose it at the exact seam where evidence enters a model call, and the run manifest records only `sourceBundle.packageId`/`refs[]` at package granularity, so a run cannot be reconstructed to the unit that supplied a given context item.
- Evidence: `"ref": { "properties": { "sourceId": …, "sourceUnitId": …, "locator": { "type": "string" } } }` (agent-runtime schema L70–78) vs `locator` as an object with `kind`/`start`/`end`/`value` (source-map schema L29–44).
- Suggested direction (not a mandate): define the provenance shape once and reference it, or state explicitly that `input[].ref` is a lossy projection and say what is dropped.

### CH-10 — `outputSchemaRef` has no version while `promptRef` is required to, for the same reproducibility reason
- Severity: major
- Confidence: CONFIRMED
- Location: `schemas/agent-runtime.v0.1.schema.json` `outputSchemaRef` (L84–93, `required: ["id"]` L91); `specs/agent-runtime-v0.1.md` §5.3 (L191–193), RT-11 (L311), §6 (L281–287); `specs/run-manifest-v0.1.md` `versions.schemas` (L107) and example L214
- Problem: RT-11 and the removal of any alternative state: "`promptRef` … always required. `promptText` alone is insufficient because an unversioned prompt cannot be recorded in a run manifest." The identical argument applies to the schema a run validates against — the manifest records `versions.schemas` precisely so comparisons are valid (RM-1) — yet `outputSchemaRef` requires only an unconstrained `id`. The convention that saves it (`{"id": "source-map/0.1"}`) is only a convention: `{"id": "source-map"}` validates, and the schema file's own identity (`source-map.v0.1.schema.json`, `$id` …`/schemas/source-map.v0.1.schema.json`) is a third naming scheme.
- Why it matters: A run can be recorded as validated against "the source-map schema" while the schema was edited between runs, with nothing in the request, the result or the manifest recording which revision was used. That is the comparison invalidity RM-1 exists to prevent, and it is silent.
- Evidence: `promptRef.required: ["id","version"]` (L55) vs `outputSchemaRef.required: ["id"]` (L91).
- Suggested direction (not a mandate): require a version (or a digest) on `outputSchemaRef`, consistent with how the manifest already keys `versions.schemas`.

### CH-11 — Referential integrity is asserted as contract but enforced nowhere
- Severity: major
- Confidence: CONFIRMED
- Location: `specs/source-map-v0.1.md` L144 ("Must resolve to an entry in `sources[]`") and `src/contracts/source-map.ts` L180; `schemas/source-map.v0.1.schema.json` `units[].sourceId` (L116, bare `minLength: 1`), `conflicts[].unitRefs` (L185); `schemas/semantic-card.v0.1.schema.json` `evidenceRef.sourceUnitId` (L18–21), `relations[].target.knowledgeId` (L143); `tools/check.ps1` L445–476 (well-formedness only) and `schemas/README.md` L46–48, L54–59
- Problem: Every cross-reference in the four contracts (`units[].sourceId` → `sources[]`, `conflicts[].unitRefs` → `unitId`, `evidenceRefs[].sourceUnitId` → a SourceMap unit, `relations[].target.knowledgeId` → a card, `disposition.knowledgeRefs` → cards) is a bare string with no constraint beyond non-emptiness. JSON Schema cannot check them, so the check must live in a validator — and no validator exists, is specified, or is listed as a deliverable; `tools/check.ps1` validates JSON well-formedness and a `DRAFT` marker, and `schemas/README.md` "Known gaps" confirms there is no instance validation. The drafted examples already demonstrate the gap: the SemanticCard example cites `sourceUnitId: "su.lecture03.0042"` (`specs/semantic-card-v0.1.md` L271) while the SourceMap example defines `0011`, `0017`, `0019`, `0022` (`specs/source-map-v0.1.md` L274, L289, L303, L314) — the only worked cross-contract reference in the contract set dangles.
- Why it matters: `SEM-LINK-BROKEN` ("Card points at a missing note, evidence item or relation") and `EVID-PROVENANCE-LOST` are named failures in `ERROR_TAXONOMY.md` (L41, L64) that these contracts present as resisted. Until a referential check is specified, "the schema validated" means nothing about whether anything is actually connected, and the drift is undetectable by the repository's own check script.
- Evidence: `"sourceId": { "type": "string", "minLength": 1 }` (source-map schema L116) vs spec L144's "Must resolve"; `tools/check.ps1` performs `ConvertFrom-Json` and a DRAFT-marker regex (L459–470) and nothing else.
- Suggested direction (not a mandate): name the referential check as a required artefact of the next milestone (even as a TODO in `schemas/README.md`), since the contracts currently read as if it already existed.

### CH-12 — `learningAssets[].ref` may be empty, so the pedagogical index can point at nothing
- Severity: major
- Confidence: CONFIRMED
- Location: `schemas/semantic-card.v0.1.schema.json` `learningAssets` (L166–194: `ref` L180–188, `required: ["kind","ref"]` L191); `src/contracts/semantic-card.ts` `LearningAssetRef` (L179–183); `specs/semantic-card-v0.1.md` SC-5 (L67–75), Q8 (L371)
- Problem: `ref` has `additionalProperties: false` but no `required` and no `anyOf`, so `"ref": {}` validates — an asset classified as `definition`, `common-mistake` or `mnemonic` that identifies no location, with no `sourceUnitId`, no anchor and no path. Unlike `evidenceRef` (which at least demands a key) and unlike `locator` (where `kind` is required), the asset index has no identifying constraint at all. There is also no `basis`, no `confidence` and no per-asset epistemic state, so the classification itself ("this region is a mnemonic, not a definition") is an untraceable machine assertion.
- Why it matters: SC-5 justifies the asset index as the mechanism that keeps analogies, tips and common mistakes findable after summarisation, and cites `LSN-ANALOGY-AS-FACT` / `LSN-OPINION-AS-FACT` / `LSN-HEURISTIC-AS-THEOREM` as the failures it prevents. A `{}` ref satisfies the contract while providing no way to find or verify the asset; worse, `kind: definition` on an unlocatable entry is exactly the "analogy filed as the concept" failure F5 claims is prevented.
- Evidence: `"required": ["kind", "ref"]` (L191) with `ref` properties `anchor`/`sourceUnitId`/`path` and no requirement clause (L180–188). Q8 asks whether `ref` may point at evidence instead of a note anchor; it does not ask whether `ref` may point at nothing.
- Suggested direction (not a mandate): require at least one identifying member, and consider whether `kind` needs the same basis/confidence treatment as claim state.

### CH-13 — Card-level `epistemicState` is an untraceable assertion and a duplicate of per-claim state
- Severity: major
- Confidence: CONFIRMED
- Location: `schemas/semantic-card.v0.1.schema.json` `epistemicState` (L162–165, in root `required` L231); `src/contracts/semantic-card.ts` L252–253; `specs/semantic-card-v0.1.md` §5 (L214, "Coarse roll-up; per-claim state is authoritative"), §3 (L146), Q2 (L365)
- Problem: The card-level state is required, is drawn from the same vocabulary as `claims[].epistemicState`, and has no `basis` field, no evidence slot and no defined relationship to the claims it summarises. Two consequences: it is an assertion with no traceability mechanism (SC-2), and it is a second place where "the same fact" lives, with no derivation rule and no consistency constraint. A card whose only claim is `inferred` may declare `epistemicState: verified`, and nothing — schema or prose rule — makes that a defect. ### CH-29 — The agent-runtime machine contract is an empty envelope, and the interface it describes is not in the schema at all
- Severity: nit
- Confidence: CONFIRMED
- Location: `schemas/agent-runtime.v0.1.schema.json` root (L229–237: `required: ["contractVersion","status"]` L236); `src/contracts/agent-runtime.ts` `AgentRuntime` interface (L230–240) and `AgentRuntimeBoundaryDocument` (L243–248); file header claim "Mirrors `schemas/agent-runtime.v0.1.schema.json`" (L4–5); check.ps1's required-file list (L288–292)
- Problem: The schema root requires only a version and a review status, so `{"contractVersion":"agent-runtime/0.1","status":"draft"}` is a valid instance of the contract that is supposed to describe the runtime boundary. `runtimeMetadata`, `taskRequest` and `invocationResult` are all optional, and the TS file's central artefact — the `AgentRuntime` interface with `metadata` and `invoke()` — has no schema representation at all; validating a request requires reaching into `#/$defs/taskRequest`, which no spec or README mentions. `status` on this envelope is also hard to fill meaningfully: unlike the other three contracts, nothing here is a stored, reviewable artefact, so `reviewed` describes a transient call. This is the one contract of the four whose root is not the primary artifact.
- Why it matters: An implementer who validates against the published schema will validate an empty wrapper and conclude the request was well-formed. The "TypeScript mirror" claim is loose for this contract specifically, and a reader cannot tell from the schema whether a `TaskRequest`, a `RuntimeResult`, or the envelope is *the* contract.
- Evidence: `"required": ["contractVersion", "status"]` (L236) with the other three properties optional (L232–234).
- Suggested direction (not a mandate): publish `taskRequest`/`runtimeResult` as the addressable contract and say so in the spec header, or require the payload at the root.

### CH-30 — `output.format` is a runtime-side judgement the core cannot verify, from a runtime that must not parse
- Severity: nit
- Confidence: CONFIRMED
- Location: `schemas/agent-runtime.v0.1.schema.json` `runtimeResult.output` (L160–172, `raw` L163, `format` L164, `parseError` L165–168, `required: ["raw","format"]` L170); `specs/agent-runtime-v0.1.md` RT-6 (L54–60), §5.4 (L210–213)
- Problem: RT-6 says the runtime must not validate, repair or reject output — and the design reason is that malformed output is "the most valuable failure signal", which belongs to the core. Yet the runtime is required to label `format` as `json`/`text`/`unknown` and may set `parseError` "when the text could not be parsed at all". Labelling text as `json` requires attempting to parse it, and setting `parseError` requires having parsed it — so the boundary depends on a parse judgement made by the component the contract says must not make judgements about the output. There is no field by which the core can distinguish "the runtime parsed this and it was JSON" from "the runtime guessed `json` from a leading brace".
- Why it matters: `output.format` is required, so the core must consume a machine classification it cannot corroborate; a wrong `json` label on unparseable text steers the core's error classification in the wrong direction, and the failure signal RT-6 wants to protect is filtered through the runtime before the core sees it.
- Evidence: `"required": ["raw", "format"]` (L170) alongside `"parseError": { "description": "Set when the text could not be parsed. Not itself a runtime failure." }` (L165–168).
- Suggested direction (not a mandate): define `format` as a declared claim with a stated origin, or make it advisory (`formatSource`) so the core knows whether it must re-derive it.

## What looks sound

- **The declared data direction Card → SourceMap is genuinely one-way in the schemas.** `SemanticCard` references SourceMap unit ids (`evidenceRef.sourceUnitId`, `relations[].target.sourceUnitId`); the SourceMap schema references no card structure and no card type. CH-05 is the one exception and it is confined to `disposition.knowledgeRefs`.
- **No DSH-specific artefact leaks into the machine contracts.** No DSH type, session concept, CLI name, version literal or install path appears in any of the four schemas or in `src/contracts/*.ts`; the boundary shapes themselves (`TaskRequest`, `RuntimeResult`, `RunError`) are neutral and RT-21 holds for their contents.
- **Error classification is well designed.** `RunError` kinds with `retryable` + `stage`, and `RuntimeInvocationResult` as a discriminated union, do what RT-7 claims: an empty result (`model-returned-empty`) is not confusable with a transport failure, and the failure branch cannot be silently ignored. The `if/then` in `invocationResult` is also the one place the schemas use conditional validation — which is what makes CH-01/CH-03's gaps look like oversights rather than tool limitations.
- **`Usage.availability` is the right idea**, and `model-identity`'s requested/resolved/resolution trio is the correct shape for making substitution visible (the problem is only that the runtime case has no "requested" side — CH-04).
- **The counterexample tables do real work.** F1–F12 in each spec are specific, and several correctly identify that their mitigation is partial (SC F9, SM F7, RM F2). Honest ambiguity sections (SC A5/A6, SM A2/A4/A7, RM A4/A7, RT A2/A3) are the reason several of my findings are graded minor rather than major.
- **Scope discipline is respected.** Nothing in the four specs pre-empts LessonModel, alignment, ChangePlan, the writer or the plugin, and `docs/DECISIONS.md` D-0010's "layout undecided" is honoured consistently — no contract field names a file location for a card or a map.

## Questions the contracts cannot answer

1. **Who validates instances, and when?** `SC-14`, `SM-A5`, `RM-A2/A3`, `SC-7` and CH-01/CH-03/CH-11 all defer to "a future validator" that no milestone names. Until a validator (and its rules for referential integrity, non-emptiness, and dependent requirements) is scheduled, is the JSON Schema the contract or a partial sketch? (CH-01, CH-03, CH-11, CH-25)
2. **Is `SourceMap.disposition` written back after Layer C exists, or is the map immutable with disposition living elsewhere?** This is RM-Q2/SM-Q2 and it determines whether the current schema shape is usable at all. (CH-23)
3. **Is `claims[].anchor` mandatory, or is prose in `claims[].note` acceptable?** SC-2 and F1 say one thing; the schema and §4's "Preferred" say another. If prose is acceptable, SC-1/SC-2 must be rewritten. (CH-02)
4. **What does a manifest record as the *requested* runtime, and can `runtime.resolution` mean anything?** (CH-04)
5. **What is the single provenance shape for evidence?** Three exist; a fourth will be invented by whoever writes the DSH adapter unless the ruling comes first. (CH-09)
6. **Is `retentionClass` a Layer B judgement (and therefore required) or a Layer D judgement (and therefore downstream)?** SM-1 and the field table answer differently. (CH-06, CH-07)
7. **Does the card need a controlled classification (tags/domain/module), or are L0/L1 deliberately deferred in favour of prose matching?** Either answer is fine; leaving it unrecorded is not. (CH-27)
8. **Are requirement IDs a stable citation namespace?** If yes, every cited ID needs a definition; if not, `specs/README.md`'s rule should be withdrawn and the headers' ranges corrected. (CH-21)
9. **Is `runtimeKind` (and `implementationNote`) to be constrained, or explicitly accepted as free text?** RT-Q2 asks whether the field should exist; the unanswered part is what may go in it. (CH-16)
10. **May `unknown`/`unspecified`/`droppable` be used at scale, and does any experiment measure that?** SM-A3 concedes the loophole; a v0.1 acceptance criterion does not exist. (CH-25)
